01 · 空间关系 / STRUCTURE
01 · 进程与线程的地址空间↩ 查看本节课堂精简图

进程是资源与地址空间的组织单位；线程是执行路径

观察一片进程虚拟地址空间：三个线程可以读取同一段代码与共享堆中的缓冲队列，但各有线程栈和执行现场。内核维护管理实体所需的记录，不能把 PCB 画成用户可以随意访问的私有数据。

图中“共享”的真正含义

同一进程内的线程通常共享代码、全局变量、堆、打开文件等进程资源；这只意味着有共同访问途径，不意味着访问自动安全。

为什么必须保存线程现场？

某线程被调度走后，恢复执行需要程序计数器、寄存器、栈等上下文；进程切换还可能涉及地址空间等其他状态。

考点抓手：资源归属看进程，执行进度看线程；同一虚拟地址空间不等于同一个执行栈。

同一份机器指令，为什么能对应多个 sum() 栈帧？

沿用教材《进程在内存中的映像》（第 2 章图 2.1）的宏观视角，再把 Stack 放大到你拍摄的“caller 与 add 的栈帧”（图 4.12）那样的粒度。这里额外采用大学课程常见的 32 位 x86（IA-32）/典型 cdecl 示意来解释 EBP、ESP、call 和 ret。

零、贯穿全程的 C 代码

int a = 10;  // .data
int b;       // .bss

int sum(int n) {
    int x = n;
    if (n == 1) return 1;
    return x + sum(n - 1);
}
int main(void) {
    int result = sum(3);
    return result + a + b;
}

这是教学源代码，不是某一编译器的汇编实测结果。为了直观显示完整栈帧，下文假定不开启优化、使用帧指针，并采用栈上传参数的 32 位 x86 常见调用约定。

① 整体：一个进程的虚拟地址空间

高地址 ↑ · 教材常见布局，非精确地址

内核保留区域（视系统而定）
Stack：main → sum(3) → sum(2) → sum(1)
栈向低地址扩展 ↓ · 每次调用一个栈帧
共享库映射 / 其他映射 / 未用地址
Heap：本例未使用 malloc
.data：a=10　|　.bss：b=0
.text：main() 与 sum() 指令各一份

低地址 ↓ · 代码与栈不在同一个用途区域

② 放大：Stack 的四个活动栈帧

从高地址到低地址 ↓

main() 栈帧 · 等待 sum(3) 返回
sum(3) 栈帧 · x=3，等待 sum(2)
sum(2) 栈帧 · x=2，等待 sum(1)
sum(1) 栈帧 · x=1，正在执行
同一份 sum() 指令被多次执行 ≠ 压入多份 sum() 代码

每层压入的是这次调用需要保留的返回位置与执行状态；具体局部变量或参数可由寄存器保存，是否占栈取决于编译与调用约定。

第一层：为什么编译后有固定映像，运行后才有递归帧？

程序中的对象对应位置出现时间 / 含义
main()、sum().text编译链接后在可执行文件中有代码；装入时建立代码映射，物理页可按需调入
a=10、b.data、.bss全局对象有静态存储期，.bss 通常不需要在文件中逐字节存储零值
result、n、xStack / 寄存器随函数调用形成活动状态，编译器可优化寄存器分配
Heap本例无动态申请递归本身不等于 malloc，也不等于堆增长

不同操作系统、ABI、编译器的地址安排可能不同；教材图上的“内核区”属于典型结构示意。

第二层：把教材图中的 Stack 再放大为一帧

下表展示一个简化的 IA-32 栈帧。假设 sum(n) 采用 push ebp; mov ebp,esp; sub esp,... 等常规序言；真正汇编可能还保存寄存器、设置对齐填充等。

相对 EBP栈内存储单元（高地址→低地址）来源 / 用途
[EBP+8]n（本层参数）调用者传入，传统栈传参模型
[EBP+4]返回地址call sum 将下一条指令的地址压栈
[EBP]旧 EBP被调用者执行 push ebp 保存上层帧指针
[EBP-4]（示例）x（本层局部变量）示意采用栈槽存放，实际编译可能放寄存器
更低地址其他临时空间 / 对齐填充 / 调用参数ESP 根据当前栈布局变化
EBP 与 ESP 的分工：在此栈帧约定中，EBP 是访问这一帧参数与局部量的相对稳定基准；ESP 指向当前已分配栈顶（较低地址一端），随 push/call/sub esp 等变化。

第三层：同一段 sum() 指令对应三个活动栈帧

.text：只存一份

sum:
  ...        ; 判断 n
  ...        ; 保存本层 x 等状态
  call sum   ; 再调用同一入口
after_call:
  ...        ; 使用子调用返回值
  ret

这是解释调用位置的伪汇编，不是对 C 程序逐条实际反汇编。

Stack：三份未结束的状态

sum(3) · n=3，x=3；保存自己尚未完成的加法
sum(2) · n=2，x=2；等待更深层返回
sum(1) · n=1，x=1；执行基例 return 1

递归中 sum(2) 和 sum(1) 的返回地址可以都指向 .text 中 sum 的 after_call；但返回时恢复的 EBP/ESP 和对应栈帧不同，因此仍会取得各层自己的 x。

第四层：函数调用的精确事件顺序（以典型 32 位 x86 为例）

1 · main 调用 sum(3)：准备参数；call sum 把“返回到 main 的地址”压栈并跳到 .text 中 sum 入口。
2 · sum(3) 进入：push ebp 保存旧 EBP；mov ebp,esp 建立本层基址；需要时给 x/临时值留空间。
3 · sum(3) 调用 sum(2)：它尚未算完，要保留本层 x=3 及返回信息；新调用进入 sum 的同一段机器指令，但新栈帧属于 n=2。
4 · sum(2) 调用 sum(1)：形成第三个 sum 栈帧，栈继续向低地址扩展。
5 · sum(1) 返回：返回值 1 通常置于 EAX；恢复被保存的帧指针/栈指针，ret 弹出返回地址并跳回 sum(2)。
6 · 逐层退栈：sum(2) 取得 1 后算得 3；sum(3) 取得 3 后算得 6；最终返回 main。帧结束不等于内存字节自动清零。
数值位置的关键：return 的整数结果在常见 IA-32 约定中通过 EAX 传递；不能笼统说“每一层 sum 的结果都压在栈上”。栈的主要职责是保留未完成调用的上下文。

第五层：用你拍的教材栈帧图核对三个问题

教材图 4.12 的对象本例对应考点
caller P 局部变量 temp1/temp2/summain 的 result、外层 sum 的 x局部变量属于相应调用的状态
传给 add 的参数 80、125调用 sum 时的 n=3/2/1参数可以占用不同于局部变量的存储位置
call 压入返回地址sum 的下一条指令 / main 的续接位置返回点属于代码段地址，地址值保存在栈中
被调用者保存旧 EBP每层 sum 保存上一层 EBP建立帧链，返回时恢复调用者状态
add 的返回值经 EAX 返回sum 的 1、3、6 经 EAX 逐层返回寄存器与栈是两个不同位置

边界：上述偏移和 EBP/ESP/EAX 是典型 IA-32 教学模型。x86-64、ARM 等体系结构传参规则可能完全不同；帧指针可省略，尾调用优化也可能改变栈深。

下载线程等待网络数据时，CPU、内核和设备发生了什么？

不能把“进入内核态”“线程阻塞”“进程切换”“设备中断”画成同一种箭头。这些是不同性质的事件；时间泳道允许它们同时出现在一条时间线上。

最容易错的两个判断：进入内核态不必然切换进程；设备完成后，等待线程通常先进入就绪态，未必立刻获得 CPU。

CASE 02 / 04A · 进程间通信 · IPC

两个不同进程怎样通信？四种典型机制

共享内存：共同映射

不同进程原本有各自的地址空间，建立共享映射后，两个虚拟地址可以指向同一物理页。双方可以直接读写共享区域，但需要互斥与同步。

// 伪代码，忽略创建与映射参数
A: shared->value = 42;
B: printf("%d", shared->value);

消息传递：发送与接收

通过操作系统提供的消息队列、端口或通信对象执行 send/receive，不要求共享同一个可写数据页。消息可能具有边界，是否阻塞依接口而定。

A: send(channel, "OK");
B: receive(channel, buf);

管道：写端与读端

常见匿名管道是经文件描述符读写的单向字节流，内核提供缓冲。管道空、满或写端关闭时，读写行为不同。

// 伪代码：父子进程继承合适的 fd
A: write(pipefd[1], "OK", 2);
B: read(pipefd[0], buf, 2);

信号：事件通知

如 SIGTERM、SIGUSR1 等，可向进程发送事件通知。它不适合承载大块数据，通常也不提供普通消息队列那样的完整数据传输语义。

A: kill(pidB, SIGUSR1);
B: // 已安装信号处理方式
三条 408 判断：① “共享内存通信”专指进程间经过建立共享映射等机制共同访问数据，不能把所有线程共享变量都称为 IPC。② 管道与消息队列都可用于通信，但管道通常提供字节流，消息队列有独立的消息边界。③ kill() 发送的 Signal 与 P/V 操作的 Semaphore 不是同一种机制；后者是同步原语。

05 · 约束关系 / SYNCHRONIZATION
05 · 生产者—消费者信号量↩ 查看本节课堂精简图

三个信号量分别约束什么？为什么 P/V 顺序不能随便换？

将生产者与消费者代码并排放在缓冲区两侧，便于把每一个 P/V 与它保护的实际资源对应起来。

empty = 2

初始有两个空槽；生产者写入前必须取得空槽。

full = 0

初始没有可取数据；消费者取出前必须等待有产品。

mutex = 1

保护对共享缓冲区管理状态的临界区访问。

代码的两个重点

生产者：
P(empty); P(mutex);
放入数据;
V(mutex); V(full);

消费者：
P(full); P(mutex);
取走数据;
V(mutex); V(empty);

假设使用经典记录型信号量模型。

同一段代码的数值推演

这里记录型信号量允许计数变为 −1，表示有一个等待者。生产者把 full 从 −1 增加到 0 时会唤醒等待者；等待者继续先前 P 操作后的代码，不需要再执行一次 P(full)。

如果生产者先持有 mutex，又因缓冲区满而等待 empty，它可能阻止消费者进入临界区，从而无法腾出空槽。通常应当先等待资源计数，再进入互斥临界区。

07 · 资源依赖 / RESOURCE GRAPH
07 · 资源等待与死锁↩ 查看本节课堂精简图

什么时候“两个任务在等待”真的构成死锁？

圆形表示任务，方形表示资源。资源指向任务说明已分配，任务指向资源说明正在请求。应先读懂边的方向，再判断是否形成循环等待。

若 R1、R2 都是单实例独占资源，A 占有 R1 等待 R2，B 占有 R2 等待 R1，并且既不能主动推进也不能强制剥夺资源，就形成死锁。它满足互斥、请求并保持、不可剥夺、循环等待四个必要条件。

不能从“有环”无条件推出死锁：对于多实例资源，资源分配图有环仍可能存在可继续运行的进程。银行家算法还必须与死锁检测区分：它判断假设分配后的安全性，而不只是寻找当前请求环。

08 · 章节连接 / HOW TO THINK
08 · 四种关系总复述↩ 查看本节课堂精简图

把第二章知识记成四种不同的关系，而不是一条长流程

① 空间上：谁拥有什么？

进程地址空间、PCB、共享堆、独立线程栈、内核线程映射。

② 时间上：谁在执行？

就绪、运行、阻塞；CPU 调度、上下文切换、I/O 完成通知。

③ 数据上：谁依赖谁？

共享缓冲区、管道、消息传递；同步与互斥；管程条件变量。
