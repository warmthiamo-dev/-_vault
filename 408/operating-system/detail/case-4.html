一次打开文件，经过哪些层次？

文件系统将“名字与逻辑块”转为“设备上的物理块”

案例起点：双击错题总结.docx

用户提出的是“打开指定文件”，而硬件只处理块和设备命令。文件系统必须把用户级操作逐步转换成目录查找、元数据定位、数据块映射以及底层 I/O。

  1. 逻辑文件系统：处理文件名、目录、权限与 FCB/inode 等管理信息。
  2. 文件组织模块：把文件逻辑块映射到具体磁盘块，并协调分配与空闲空间。
  3. 基本文件系统与 I/O 软件：通过缓存、块 I/O 和驱动与控制器协作。
本章要区分两组概念：逻辑结构回答用户怎样组织记录；物理结构回答记录的数据最终放在哪些磁盘块。

文件内部的记录怎样查找？

顺序文件与索引顺序文件

具体情境：查找“操作系统错题编号 250”

假设有 1000 条按编号排序的错题记录。如果采用顺序文件，从头逐条比较，最坏情况可能比较到最后一条；如果建立一个“每 100 条记录对应一个索引项”的索引顺序文件，就先通过索引找到可能所在的记录组，然后在组内继续查找。

索引项不必对应单条记录，可以对应一组；使用稀疏索引时尤其如此。索引记录本身也要占存储空间，且更新数据后可能需要维护索引。

不要混淆：这里的“索引”是逻辑记录查找索引；后面 inode 的直接/间接索引是文件逻辑块到磁盘数据块的索引，单位不同。

路径怎样变成一个具体文件？

目录树 · 绝对路径 · 相对路径

具体情境：打开 /考研/操作系统/错题.docx

  1. 从根目录开始，查找 考研 的目录项。
  2. 进入该目录，查找 操作系统。
  3. 在目标目录中查找 错题.docx。

文件已经打开，谁保存读取位置？

教材两级文件表：每进程打开表 → 系统级打开表 → inode / FCB；再辨析共享与独立打开

文件打开：从 read(fd) 到磁盘上的文件控制信息

按教材图 4.16：用户程序执行 read(fd)，内核先在该进程的描述符表中定位表项，再找到系统级打开文件表的对应打开信息，最后根据 inode / FCB 定位数据块。

系统级打开文件表：共享表项 vs 两个独立表项

独立打开时，写入的字节区间可能重叠

同一文件被两个进程打开时，计数在哪里？

共享同一个打开实例

如适当的 fork() / dup()：两个描述符引用一个系统级表项，表项可有引用计数 2，偏移也共享。

分别独立 open()

两个描述符引用系统级表中的不同打开实例 X、Y，各自有偏移；它们仍可引用同一 inode。

教材有时把“系统打开表”抽象成每个文件一项，其中 Open Count 表示有多少打开引用；在典型 Unix/Linux 的“每次打开实例”模型中，每个打开实例又有自己的引用计数。两种计数的对象不完全相同。

按教材图 4.16，打开文件经历哪些步骤？

① 根据路径逐级定位目标文件的目录项和 FCB / inode，并检查访问权限；② 查找或建立相应内核打开文件管理信息；③ 在发起调用的进程打开文件表中建立描述符到系统级打开信息的关联；④ 将描述符返回给进程；⑤ 以后通过 read(fd) 查表访问，减少反复路径解析。

系统级打开表记录哪些信息？

教材强调其管理与进程无关的文件信息，例如文件位置、文件大小、访问时间以及 Open Count。具体操作系统还会区分全局文件元数据缓存和每次 open() 的打开实例。后者可包含当前偏移、打开标志和引用计数，因此不能简单说“同一个 inode 就一定共享偏移”。

计数怎么变化？

在教材的按文件汇总模型里，两次打开同一文件可以让对应文件的打开计数增加；在典型 Unix/Linux 打开实例模型里，A、B 分别 open() 会产生两个打开实例（各有自己的偏移），而 dup() 可让一个打开实例的引用计数增加。close() 释放该描述符的引用；最后一个引用消失后，对应打开实例可被回收。不要把 inode 的链接计数与打开引用计数混同。

计数对照：打开文件 ≠ 创建硬链接

① User1 建文件Open 0 · Link 1
② A、B 打开Open 2 · Link 1
③ User2 建硬链接Open 2 · Link 2
④ A 关闭Open 1 · Link 2

计数对象不同：Open Count 统计打开引用；Link Count 统计指向同一 inode 的目录项。User2 仅打开文件，不会使 Link Count 增加。

沿用 User1 / User2 的同一文件例子，逐步观察两种计数

下面采用教材的按文件汇总打开计数的简化模型，而非绑定某个具体操作系统的内核字段。假设文件 User1/笔记.docx 刚建立时，有一个目录项指向 inode #42。

为什么同一个 inode 会有两个计数？

打开计数回答“现在有多少次打开引用仍在使用它”；硬链接计数回答“文件系统目录里还有几个名字指向这个文件”。它们服务于不同的生命周期判断。关掉最后一个打开引用并不会自动删除文件名；删除最后一个文件名，也不意味着正在打开的文件必须在那个瞬间立即失去所有使用者。

一个很容易混淆的条件

User2 仅登录、访问或打开 User1 的同一文件，不会让硬链接数由 1 变成 2。只有 User2 通过允许的操作在目录中新建一项硬链接，才增加指向这个 inode 的目录项数量。该模型假设操作发生于允许硬链接创建的同一文件系统内。

和前面的“共享文件偏移”有什么关系？

它们是三种不同的统计对象：文件的硬链接数属于 inode/目录项关系；教材的Open Count是对文件打开引用的汇总；打开实例的引用数则决定多个描述符是否指向同一个打开实例、从而是否共享同一读写偏移。不能因为都叫“引用计数”就把它们混成一个数字。

教学组织参考：MIT 文件系统讲义（全局打开计数）；Stanford CS110（inode 的硬链接计数）；Stanford 文件描述符及系统打开表。计数的内核实现依系统而异，本例按教材简化抽象推演。

对照 1：fork / dup 共享打开实例

假定同一个打开实例当前偏移为 100。A 成功执行 write(fd,buf,101) 后，共享偏移通常变成 201；B 接着用普通 write(fd,buf,20) 会从 201 开始，写完变成 221。B 不会自动使用“自己的偏移 200”，因为此场景根本没有两个独立的打开实例。并发执行时需要额外考虑写入的原子性与同步规则。

对照 2：A、B 分别 open 同一个文件

如果 A 的打开实例偏移为 100，B 的偏移为 200，那么 A 写入 101 字节覆盖字节 100～200；B 写入 20 字节覆盖 200～219。字节 200 重叠 1 字节。两个实例的文件偏移各自变化，但底层 inode 指向的是同一个文件内容。没有加锁或协调时，写入冲突可能由覆盖顺序决定，不能简单保证整次并发写入必然“后调用者完全覆盖”。

和 Word / WPS 同时保存的区别

Office 文档不是按“每输入一个字就向原文件某个固定字节写入”来理解的。程序往往把文档读入内存，修改自己的文档模型，再在保存时重写或替换文件；可能采取文件锁、只读提示、冲突检测或协同编辑方案。因此“两个打开实例偏移独立”不等于“两个软件各自修改的内容会自动合并”。

记忆：文件描述符属于进程；偏移属于打开实例；持久文件内容由底层文件对象管理；互斥/锁解决并发访问协调问题。

具体情境：Word 和另一个程序都打开同一份文件

进程打开表中的描述符（例如 3）用于在本进程内引用打开文件；系统级打开文件表项可记录当前偏移、访问模式等；inode 保存文件元数据及其数据块定位信息。

上面的第一幅对照图展示两个描述符指向系统级表中的同一打开实例（如适当的 fork/dup 后）；另一幅展示分别 open 同一个文件后，系统级表中有不同打开实例，但它们可以引用相同 inode。

例：当前打开实例偏移为 100，读入 20 字节后，成功读取的情况下偏移通常前进到 120；不要把偏移误认为 inode 一定保存的全局读写位置。

共享文件：硬链接与符号链接不同在哪里？

名字—inode 关系 vs 路径间接引用

具体情境：给同一份错题笔记创建两个入口

硬链接：目录项 笔记.docx 和 复习副本.docx 都引用同一个 inode，通常也对应同一份实际数据。删除其中一个名字，不代表马上删除文件数据；还要考虑其他硬链接与仍打开的引用。

符号链接：快捷入口 是独立的链接对象，它保存用于定位目标的路径；若目标被删除或路径失效，链接可能成为悬空链接。符号链接通常可以跨文件系统，但硬链接通常受同一文件系统的限制。

硬链接计数表示引用 inode 的硬目录项数量，不是打开文件的进程数。实际系统往往限制对目录创建硬链接，以防形成难以管理的环。

同一文件的磁盘块可以怎样组织？

连续 · 隐式链接 · FAT · 索引分配

具体情境：四个逻辑块的数据存在哪里？

分配方法如何定位逻辑块 k优点主要限制
连续分配已知起始块 b，目标块通常为 b+k随机访问方便，局部性好外部碎片，增长受相邻空间限制
隐式链接由前一块的后继指针沿链寻找分散空闲块容易利用随机访问差，链指针损坏有风险
FAT在卷级表中按照块号追踪后继FAT 缓存时可在内存中追链表的容量、维护与可靠性问题
索引分配通过文件索引块按逻辑块号取块地址便于随机定位索引块自身需要存储空间

例：起始块为 100、逻辑块号从 0 开始，连续分配下逻辑块 3 位于物理块 103；换为隐式链接后，不能再直接用 100+3 计算。

FAT 一般是一个卷共享一张表，不是每个文件一张；FAT 已在内存时，不必为追踪每条链指针而逐个读取磁盘数据块。

读取逻辑块 1036，为什么走二级间接？

12 个直接块 + 1 个一级间接 + 1 个二级间接

题设与完整推导

采用 PDF 第 72 页的自编复算例：块大小 4 KiB，每个指针 4 B，inode 有 12 个直接指针、一个一级间接指针和一个二级间接指针，逻辑块号从 0 开始。

每个索引块指针数 = 4096 ÷ 4 = 1024
区域覆盖的逻辑块号数据容量
12 直接块0～1148 KiB
一级间接12～10354 MiB
二级间接1036～10496114 GiB

访问逻辑块 1036：先减去直接索引的 12 块和一级间接的 1024 块。

1036 − 12 − 1024 = 0

现在是二级间接区域的相对编号 0：0 ÷ 1024 = 商 0、余 0，所以找到二级索引块第 0 项对应的一级索引块，再取其第 0 项所指数据块。

如果 inode、二级索引块和一级索引块都未缓存，那么为读取最终一个数据块，可能需要读取 两级索引块 + 数据块；是否还需要读 inode 要依据题目条件，不能一概而论。

错误做法：直接用 1036 ÷ 1024 求商余而不先扣前面的直接、一级区域；另外不要把二级索引块本身计入文件数据块容量。

新增文件内容，空闲块从哪里来？

分区与卷 · 超级块 · 空闲表 · 空闲链表 · 位示图 · 成组链接

文件系统如何记录“哪些磁盘块还没被占用”？四种方式同题比较

具体情境：保存新写入的 20 页错题

文件系统需要为新增数据找到可分配的磁盘块。典型磁盘布局中，超级块描述文件系统信息，inode 区管理文件元数据，数据块区保存文件内容，空闲位示图或其他结构描述哪些位置可用。实际布局依文件系统格式而定。

假设一行位示图为 32 位，位图行号 i 和行内位号 j 都从 0 开始，则数据块号：

b = 32i + j

对于 i=5、j=3，得到 b=163。反向定位某块：i = ⌊b/32⌋，j = b mod 32。做题先确定 0/1 哪个表示空闲，以及下标是否从 0 开始。

成组链接法

把空闲块号分组管理；一组用尽后根据后续组信息继续分配，避免必须始终维护庞大的完整空闲表。组内的空闲块号和指向下一组的控制信息，需要按题目指定格式区分。

① 空闲表法：连续空闲区间的起点 + 长度

假设空闲块为 4、5、6、12、18、19、20，可以写为 (起点4,数量3)、(起点12,数量1)、(起点18,数量3)。适合发现连续空间；分配或回收后可能需要分裂、合并空闲区间。它统计的是空闲盘块，不是文件分配表 FAT。

② 空闲链表法：把空闲块作为节点串起来

示意 4 → 5 → 6 → 12 → 18 → 19 → 20。管理者持有链头，分配可从链中取空闲块；查找较大连续空闲区并不方便，某些实现会增加访问开销。注意与“文件的链接分配”区分：前者链接的是空闲块，后者链接的是某个文件已占用的数据块。

③ 位示图法：每个磁盘块对应一个二进制位

本例规定 0 表示空闲、1 表示已分配。若位图每行 32 位，行号 i 与位号 j 都从 0 开始，则 b=32i+j；第 5 行第 3 位映射为块号 163。题目如果改变 0/1 含义、按 1 编号或者先给出偏移地址，必须先换算再判断。

④ 成组链接法：成组存储空闲块号，组与组相互衔接

示意图只表达结构：内存中的空闲块号栈维护一组可分配块号，在达到组边界时通过存于磁盘的下一组索引信息继续管理。与单纯空闲块链相比，避免每次只拿一个块号就必须沿磁盘指针追踪；但具体栈容量、链接信息占用哪个位置、组满/组空时如何入栈出栈取决于教材约定，不应把图上数字当作统一算法规则。

把四种方法放在同一道题中

“申请 3 个连续块”时，空闲表可直接发现区间 4～6 或 18～20；位示图需要检查连续零位；空闲链表需要检查链上块号是否连续；成组链接则先得到可分配块号，再根据实现选择是否能满足连续分配。它们记录空闲空间的方法不同，不决定文件本身采用连续、链接还是索引分配。

为什么同一 write() 能访问不同文件系统？

VFS 统一接口，具体文件系统实现底层操作

具体情境：同一个编辑器可以保存到多种格式的存储卷

应用程序发起 write()，内核通过打开文件对象及相关操作表/文件系统对象，转入具体文件系统的写入实现。后续可能经过缓存、块 I/O 和设备驱动。

VFS 使普通程序能够使用统一的文件操作接口；但不同文件系统对文件大小限制、权限语义、持久化与性能等方面可能不一致。

详解 10 / 11 · PDF 第 73 页 · VFS 与挂载

为什么挂载后，同一个目录里看到的文件变了？

一个路径入口，先后连接到不同文件系统的目录树

沿着图中的同一条路径走三次

假设文件系统 A 已经在使用，它的目录 /mnt/data 里原本有 旧笔记.txt。另一个文件系统 B 已经格式化，根目录里有 数学.pdf 和 英语.pdf。这里的 A 和 B 是两套文件系统，并不是两个普通文件夹。

  1. 挂载前：从 A 的根目录 / 开始查找 mnt → data → 旧笔记.txt，因此 ls /mnt/data 看见旧笔记。B 的文件仍在 B 中，但没有通过这条路径接入。
  2. 建立挂载：例如在典型 Linux 命令环境中使用 mount /dev/sdb1 /mnt/data（设备名只作示例）。内核记录“这个挂载点对应文件系统 B 的根目录”。没有把 B 的 PDF 复制到 A 的目录中。
  3. 挂载后：路径查找到 A 的 /mnt/data 时，VFS 发现这里有挂载关系，于是跨入 B 的根目录。后面的文件名在 B 中继续查找，因而 /mnt/data/数学.pdf 能访问 B 中的数学文件。A 中的 旧笔记.txt 只是暂时被遮蔽。
  4. 卸载后：例如 umount /mnt/data，解除这条挂载关系；这时路径又通向 A 原本的 data 目录，所以旧笔记重新出现。卸载时若文件系统正被占用，操作系统可能拒绝卸载。

把 VFS 的作用定位在“查路径的中途”

应用程序请求打开 /mnt/data/数学.pdf，VFS 并不知道文件一定来自哪个磁盘。它先处理统一的路径查找和文件操作接口；遇到 /mnt/data 这个挂载点时，根据挂载信息转到文件系统 B，再由 B 的具体文件系统实现查找、读取对应文件。

三个不要混淆：① 格式化是建立文件系统结构；② 挂载是把已有文件系统接入某个路径；③ 打开文件是在已经形成的目录命名空间中定位某个文件。挂载不会自动复制文件，也不会删除挂载点原有内容。

单击保存后，数据真的落盘了吗？

打开、定位、缓存、写回、持久化不是同一瞬间

完整场景：编辑“错题.docx”并点击保存

  1. 应用程序通过文件句柄或文件描述符发起写入，内核找到关联的打开实例。
  2. VFS 分派到具体文件系统；文件系统需要定位或分配目标数据块，并可能更新 inode 等元数据。
  3. 在常见缓存写入模型下，新数据先进入内存缓存，被标记为待写回。
  4. 系统在适当时机把数据或元数据提交给存储设备，设备再完成相应处理。
  5. 若需要更强的数据持久化保证，应遵循系统提供的同步接口及其语义。
本图是典型“写回缓存”教学模型。不是所有写入路径都严格按这条轨迹（例如直接 I/O、同步写策略等）。另：实际 Word 可能采用“临时文件 + 重命名”等安全保存流程，不能机械等同于单个 write()。
